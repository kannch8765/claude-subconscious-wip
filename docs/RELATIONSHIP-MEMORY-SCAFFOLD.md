## 1. Product purpose

This project is not a second general-purpose work-memory system. It does not initially target project status, TODOs, generic workflow preferences, or ordinary user-profile facts.

Its first product purpose is to preserve a shared conversational world:

- personal experiences described by the user;
- shared experiences that acquire meaning between the user and assistant;
- relationship events that clarify or change the relationship;
- inside jokes, callbacks, and shared language.

The first scaffold recognizes exactly four canonical memory kinds:

```text
personal_experience
shared_experience
relationship_event
inside_joke
```

No additional kinds are authorized by this document.

## 3. Memory authority boundary

The authoritative memory store must contain structured canonical records and bound evidence.

```text
structured canonical memory records
= authority

source evidence and user quotes
= authority

Letta Markdown memory blocks
= read-only, rebuildable projection

agent-generated guidance
= temporary suggestion, not authority
```

The memory agent must not directly edit the authoritative database, JSONL files, generated Markdown projections, or raw transcript data.

## 4. Default Markdown memory mutation

The relationship-memory agent must not retain unrestricted access to the default long-term Markdown mutation surface.

The scaffold must demonstrate that the agent cannot use these operations as an alternative write path:

```text
memory_insert
memory_replace
memory_rethink
unrestricted memory filesystem create / delete / rename / rewrite
```

Read-only projection blocks may remain visible in the agent context. A trusted renderer may update those blocks through the Letta API after canonical records change.

Read, Grep, and Glob are independent investigation tools and remain available under the existing read-only policy.

## 5. Canonical record shape

Each memory kind uses a typed payload inside a small common envelope.

The agent may propose semantic fields, but it must not generate authoritative identifiers, timestamps, identities, source quotes, or storage status.

### Common envelope

```text
memory_id          generated by the trusted backend
kind               one of the four authorized kinds
subject_id         bound by the trusted backend
participants       validated identities
summary            concise self-contained meaning
status             active / superseded / retracted
observed_at        derived from source data
created_at         generated by the trusted backend
```

### Evidence binding

Every accepted record must bind to one or more real canonical message identifiers.

```text
evidence_id
memory_id
conversation_id
message_id
role
quote
captured_at
```

The backend resolves `quote` from the referenced message. The model cannot submit or overwrite the authoritative quote text.

### Kind-specific intent

#### `personal_experience`

An experience belonging primarily to the user, such as a trip, event, discovery, or personally meaningful period.

Expected semantic fields may include:

```text
title
time range
places
themes
emotional tone
why memorable
recall triggers
```

#### `shared_experience`

An experience whose meaning is shared between the user and assistant, including symbolic gestures or moments that become part of the shared conversational world.

Expected semantic fields may include:

```text
title
participants
parent personal experience
what happened
shared meaning
symbols
recall triggers
```

#### `relationship_event`

A moment that clarifies, deepens, repairs, or otherwise changes the relationship. It is an event in a relationship history, not a final global summary of the relationship.

Expected semantic fields may include:

```text
participants
event
meaning
prior context
resulting change
linked experiences
```

#### `inside_joke`

A shared joke, callback, nickname, unusual phrase, or private meaning whose interpretation depends on conversational history.

Expected semantic fields may include:

```text
name
meaning
origin
trigger phrases
callbacks
tone
participants
```

## 6. Custom tool surface

The first implementation may expose only these two working tools:

```text
memory_search
memory_remember
```

The interfaces must reserve future compatibility for:

```text
memory_reinforce
memory_evolve
memory_get_evidence
```

### `memory_search`

Searches existing canonical records before any write attempt. It may filter by memory kind, participant, trigger, time, or semantic query.

### `memory_remember`

Proposes a new typed memory using semantic fields and real evidence message identifiers.

The trusted backend must:

```text
validate the kind-specific schema
bind the actual subject and participants
resolve evidence from canonical messages
generate IDs and timestamps
reject invented or inaccessible evidence
perform idempotency and duplicate checks
append an auditable storage event
```

The memory agent must not receive direct SQL, filesystem, or unrestricted JSON mutation tools for authoritative memory.

## 7. Projection model

Canonical records may be rendered into compact, read-only Letta blocks such as:

```text
shared_language
remembered_experiences
relationship_context
```

The projection renderer must be deterministic and must not invoke an LLM.

Recommended lifecycle:

```text
memory-agent run finishes
→ canonical revision changed
→ trusted background renderer reads active records
→ renderer rebuilds affected Markdown projection
→ trusted adapter updates read-only Letta blocks
→ projection revision advances
```

A projection can be deleted and rebuilt without losing authoritative memory.

Agent-generated `guidance` may remain separate. Guidance is not copied into the canonical store without a custom memory tool call and valid evidence.

## 9. Sanitized acceptance fixture

The first implementation must use a fictional sanitized fixture. It must not include the owner's real memories or transcript excerpts.

Example scenario:

```text
An adult user visited a historic city.
During the trip, the user selected a symbolic gift for a long-term AI companion.
The user explained why including the companion in the gesture mattered.
```

The fixture should permit the agent to propose three linked records:

```text
personal_experience
shared_experience
relationship_event
```

A separate fixture may establish one `inside_joke` record.

## 10. First scaffold acceptance

The first implementation is accepted only if it proves all of the following with sanitized data:

```text
PASS existing Letta worker/runtime can execute the configured agent
PASS the agent can call memory_search
PASS the agent can call memory_remember
PASS a valid typed canonical record is stored
PASS evidence binds to a real fixture message ID
PASS the authoritative quote is resolved by the backend
PASS replaying the same batch does not create duplicate records
PASS default Markdown memory mutation is unavailable to the agent
PASS Read / Grep / Glob remain available under read-only policy
PASS deterministic renderer produces a read-only projection
PASS canonical records remain authoritative if the projection is deleted
PASS a failed memory write does not advance the source cursor
```
